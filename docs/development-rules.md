# 開発ルール

このドキュメントでは、インターン期間中の開発におけるルールと注意事項をまとめています。

## 開発環境

### ローカル開発のみ

- 開発はすべて **ローカル環境** で行ってください
- サーバへのデプロイやテスト環境の構築は今回の対象範囲外です
- `localhost` で動作確認できる状態を目指してください

### 推奨環境

| 項目 | 推奨 |
|------|------|
| OS | macOS |
| エディタ | VS Code / Cursor / お好みのエディタ |
| ターミナル | macOS 標準ターミナル / iTerm2 |
| ブラウザ | Chrome（DevTools が使いやすい） |

## 外部サービス・ライブラリの利用

### 外部サービス連携

| 区分 | 可否 | 例 |
|------|------|-----|
| 無料サービス | ⭕ OK | Firebase（無料枠）、Supabase（無料枠）など |
| 有料サービス | ❌ NG | AWS の有料リソース、課金が発生する API など |
| 要確認 | 🔺 相談 | 無料枠があるが超過すると課金されるもの |

> **判断に迷ったらメンターに相談してください。**

### 生成 AI の利用

サービスに生成 AI 機能を組み込みたい場合：

- 発行している **Google アカウントの Gemini** を使用してください
- 個人の API キーや有料の AI サービスは使わないでください
- API キーをコードに直接書かないでください（環境変数を使う）

```bash
# .env ファイルに記載（.gitignore に含めること）
GEMINI_API_KEY=your-api-key-here
```

### 外部ライブラリ（OSS）

外部ライブラリの利用は OK ですが、以下に注意してください：

| チェック項目 | 確認方法 |
|-------------|---------|
| 信頼性 | GitHub のスター数・メンテナンス頻度を確認 |
| セキュリティ | npm audit / pip audit で脆弱性チェック |
| ライセンス | MIT・Apache 2.0 など商用利用可能なものを選ぶ |
| 最終更新日 | 長期間更新されていないものは避ける |

#### ライブラリ追加時の注意

```bash
# フロントエンド：追加後に脆弱性チェック
npm install ライブラリ名
npm audit

# バックエンド：追加後に脆弱性チェック
pip install ライブラリ名
pip audit  # pip-audit がインストール済みの場合
```

- 名前が似ている偽パッケージ（タイポスクワッティング）に注意
- ダウンロード数が極端に少ないものは避ける
- 追加したライブラリは PR の説明欄に記載する

## コーディング規約

### 全般

- コードは **読みやすさ** を重視する
- 変数名・関数名は英語で、何をするかわかる名前を付ける
- マジックナンバー（意味のわからない数値）は定数にする
- 不要なコードはコメントアウトで残さず削除する

### フロントエンド（TypeScript / React）

- コンポーネントは関数コンポーネントで書く
- 型定義を省略しない（`any` は使わない）
- `console.log` はデバッグ後に削除する

### バックエンド（Python / FastAPI）

- 型ヒントを付ける
- エラーハンドリングを適切に行う
- SQL インジェクション対策としてパラメータ化クエリを使う

## セキュリティ

### やってはいけないこと

| NG 行為 | 理由 |
|---------|------|
| API キーやパスワードをコードに直書き | 漏洩リスク |
| `.env` ファイルを Git にコミット | 秘密情報がリポジトリに残る |
| ユーザー入力をそのまま SQL に埋め込む | SQL インジェクション |
| ユーザー入力をそのまま HTML に出力 | XSS（クロスサイトスクリプティング） |

### 秘密情報の管理

```bash
# .env ファイルは .gitignore に含まれていることを確認
cat .gitignore | grep .env
```

もし `.env` が `.gitignore` に含まれていない場合は追加してください。

## チーム開発のマナー

- 作業を始める前にチーム内で担当分けを決める
- 同じファイルを複数人で同時に編集しないよう調整する
- 困ったことがあったら早めにチームメンバーやメンターに共有する
- PR は小さい単位で出す（大きな PR はレビューが大変）
- 他の人のコードを否定するのではなく、改善提案として伝える

## 困ったときの優先順位

1. **エラーメッセージを読む** — 大体のヒントが書いてある
2. **公式ドキュメントを確認する** — 一番正確な情報源
3. **チームメンバーに聞く** — 同じ問題を経験している人がいるかも
4. **メンターに相談する** — 遠慮せずに聞いてOK
