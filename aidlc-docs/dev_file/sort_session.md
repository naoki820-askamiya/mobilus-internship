# セッションソート機能

現状は、直近のセッションから表示され未対応の過去セッションが埋もれてしまう可能性がある


## オペレーターへの表示について

優先度は、自分が対応中、未対応、他人が対応中、完了済みの優先順位で実装する

ただし状態は今後増えることが予想されるため、ここの順番や種類については拡張や削除が容易でなければならない

## apiの読み取りについて

対応中、未対応については全件取得を行なって良い
完了済みは膨大な数になるため、一定件数ごと読み取るような実装にする

## 実装方針

未完了と完了済みはAPIを分離する。

- 未完了はログイン中のオペレーターを基準に優先順位を付け、全件返す
- 完了済みは件数が増えることを考慮し、直近50件だけ返す
- オペレーターの識別には既存の認証Cookieを使用し、IDやユーザー名をリクエストパラメータでは受け取らない
- 完了済みの51件目以前は取得対象外にするが、DB上のデータは削除しない

## API

### 未完了一覧

```http
GET /api/inquiries/open
```

未完了の問い合わせを次の優先順位で返す。

1. 自分が対応中
2. 未対応
3. 他人が対応中

同じ優先度では、過去の問い合わせが埋もれないように作成日時の古い順、IDの昇順で返す。

### 完了済み一覧

```http
GET /api/inquiries/closed
```

完了済みの問い合わせを、完了日時の新しい順、IDの降順で最大50件返す。
50件という上限はマジックナンバーにせず、バックエンドの設定定数として管理する。

両APIのレスポンスは、既存の`InquiryResponse`の配列とする。

## バックエンドの変更

### `backend/app/models.py`

- `mine`、`waiting`、`others`、`closed`を文字列Enumとして定義する
- 表示優先順位を1か所の定数に集約し、状態の追加や削除を容易にする

### `backend/app/config.py`

- 完了済み表示上限として`CLOSED_INQUIRY_DISPLAY_LIMIT = 50`を追加する

### `backend/app/repositories/inquiry_repository.py`

- 未完了だけを取得する`find_open()`を追加する
- 完了済みを指定件数だけ取得する`find_recent_closed(limit)`を追加する
- 完了済みはSQLの`LIMIT`で制限し、全件取得後にPython側で切り捨てない

### `backend/app/services/inquiry_service.py`

- 既存の表示ステータス算出処理を型付きのステータスに対応させる
- `list_open(operator_id)`で、ログイン中のオペレーターを基準に未完了一覧を優先順へ並べる
- `list_closed()`で、設定された上限件数の完了済み一覧を返す

### `backend/app/routers/inquiry.py`

- `GET /open`と`GET /closed`を追加する
- 静的パスが問い合わせIDとして解釈されないように、`/{inquiry_id}`より前に定義する
- 既存の`get_current_operator`を利用して認証し、オペレーターIDをServiceへ渡す
- 既存の詳細、担当取得、メッセージ取得APIは変更しない
- 既存のページング一覧APIは移行期間中は残す

### `backend/app/database.py`

完了済み一覧を効率よく取得するため、`status`、`closed_at`、`id`の複合インデックスを追加する。

## フロントエンドの変更

### `frontend/src/pages/InquiryList.tsx`

- 初回表示時に未完了APIと完了済みAPIを並列で呼び出す
- 未完了一覧の後ろに完了済み一覧を結合し、既存テーブルへ表示する
- 既存の`StatusBadge`と`AssignButton`はそのまま利用する
- ページングUIを外し、「完了済みは最新50件まで表示」と案内する
- 5秒間隔の新着検知ポーリングは未完了APIだけを対象にする
- 一覧更新時は、新たに完了した問い合わせを反映するため未完了APIと完了済みAPIを再取得する

フロント側では並び替えや50件への制限を行わず、バックエンドから返された結果を表示するだけとする。

## テスト

- 自分が対応中、未対応、他人が対応中の順で返ること
- ログインするオペレーターが変わると、自分が対応中の判定も変わること
- 同じ優先度では古い問い合わせが先に返ること
- 完了済みが最大50件であり、51件目が含まれないこと
- 完了日時が同じ場合はIDの降順になること
- 未認証の場合は両APIが拒否されること
- バックエンドテスト、フロントの型チェックとビルドが成功すること

## 今後の拡張

完了済みAPIを未完了APIから分離しているため、将来は未完了一覧やポーリングへ影響を与えず、完了済みAPIだけを次の方式へ変更できる。

- 全件取得
- カーソルページング
- 条件検索
- 専用の履歴画面
